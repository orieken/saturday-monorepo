# Data Engineering Notes: expeditions-api

## Summary

This feature needs one new flat JSON seed file (`apps/mock-api/data/expeditions.json`) and two
new additive records in the existing `apps/mock-api/data/users.json`. Both changes are
expand-only: no existing record's shape changes, no column/field is dropped or renamed, and no
runtime coupling is introduced between `expeditions.json` and `reagent-sites.json`. This confirms
and makes concrete the schema `architecture-notes.md`'s "Data Model Changes" section already
decided; nothing here revisits that decision.

## Schema Changes

### `apps/mock-api/data/expeditions.json` (new file)

Flat JSON array, one record per expedition, matching the existing `items.json` / `orders.json` /
`reagent-sites.json` convention (no ORM, no migration framework — the file itself is the schema).

| Field | Type | Notes |
|---|---|---|
| `id` | string | Stable, unique. Seed records use `expedition-seed-*`; `POST`-created records use the existing `` `expedition-${Date.now()}` `` style already used by `order-${Date.now()}`. |
| `owner` | string | Either the literal `'shop'` (seeded, shop-owned) or a `user.id` from `users.json`. **Never** trusted from a request body — `POST` always sets this from `req.userId`. |
| `from` | `{ lat: number, lng: number }` | Pre-resolved coordinate, not a site-id reference. |
| `to` | `{ lat: number, lng: number }` | Pre-resolved coordinate, not a site-id reference. |
| `savedAt` | string (ISO 8601) | Set server-side with `new Date().toISOString()` on `POST`; fixed values in seed data. |
| `name` | string (optional) | Human-readable label only — not part of the API contract (`domain-model.md` H1 is "a line and its owner"). Present on seed records for readability; `POST` does not require or accept it. |

No field is nullable-without-default and no field is being removed from an existing shape — this
is a pure **expand** addition of a new file, so the Expand/Contract pattern's phase-separation
requirement does not apply (there is nothing to contract).

### `apps/mock-api/data/users.json` (additive)

Two new records, Elara and Borin, matching the existing record shape exactly — same five fields
(`id`, `email`, `password`, `name`, `createdAt`, `address`), no shape change to the three existing
records. This is an **expand**-phase-only change: additive rows, zero existing-row mutation.

## Migration / Expand-Contract Assessment

- **No destructive operation anywhere in this feature.** No `DROP`, no `RENAME`, no removal of a
  field from an existing record.
- **No `NOT NULL`-without-`DEFAULT` risk.** These are JSON files, not a SQL schema, but the
  equivalent concern — adding a required field to existing rows with no value — does not arise:
  `expeditions.json` is a brand-new file (nothing pre-exists to backfill), and the two `users.json`
  additions are new rows with every field populated at creation, not a new column on old rows.
- **Expand phase only; no contract phase scheduled.** Nothing here deprecates or replaces an
  existing field, so there is no second migration to track.
- **Conclusion: this feature needs no migration script.** Both files are edited directly (seed
  data checked in, not generated by a migration runner) — consistent with how `reagent-sites.json`
  was seeded for `reagent-sites-api` and how `users.json` already accumulates registered users at
  runtime via `writeUsers()`.

## Query / Access Patterns for the Developer

- **`GET /api/expeditions`**: one `readJSON(EXPEDITIONS_PATH)` call, then a plain `Array.filter`:
  return every record with `owner === 'shop'`, plus — only when `resolveSessionUserId(req)`
  resolves to a non-null id — every record with `owner === thatId`. This is a single full-array
  scan over a seed-sized dataset (5 records at ship time); no pagination, index, or DataLoader is
  warranted at this scale, and none is required by `architecture-guardrails.md` #6 since this is
  not an unbounded or growing collection endpoint in the sense that rule targets — it is
  structurally identical in shape/size class to the existing `GET /api/reagent-sites` and
  `GET /api/orders` handlers, which use the same unindexed full-scan pattern today.
- **`POST /api/expeditions`**: read the full array, `push()` the new allow-listed record
  (`{ id, owner: req.userId, from, to, savedAt }` — never a spread of `req.body`, per
  `architecture-notes.md`'s structural decision), then `writeJSON()` the whole array back. This
  mirrors `writeOrders`'s existing read-modify-write pattern exactly — no partial-write or
  row-level update primitive exists in this flat-file store, and introducing one for a 5-10 record
  file would be premature generalization.
- **No N+1 risk exists**: neither handler issues a query per item in a loop; both are a single
  `readJSON` per request. `architecture-guardrails.md` #6's eager-loading requirement is
  inherently satisfied because there is only ever one "query" (one file read) per request.
- **No index is needed.** A JSON array scanned with `.filter()`/`.find()` has no index concept;
  at the file sizes this mock API operates at (single digits to low hundreds of records), adding
  one would be solving a performance problem that does not exist and that scope.paths does not
  ask for.

## Data Access Rules for the Developer (do not deviate)

1. Add `EXPEDITIONS_PATH = path.join(__dirname, 'data', 'expeditions.json')` next to the other
   `*_PATH` constants.
2. Add `readExpeditions()` / `writeExpeditions()` as one-line wrappers around `readJSON` /
   `writeJSON`, exactly matching `readOrders()` / `writeOrders()`'s existing shape — no deviation
   in error handling, since `readJSON`/`writeJSON` already centralize that.
3. `POST`'s persisted object MUST be built as an explicit field list
   (`{ id, owner: req.userId, from, to, savedAt }`), never `{ ...req.body, ... }`. This is the
   feature's trust-boundary invariant (AC11) and is a data-layer concern, not just an API concern:
   a spread would let a forged `owner` field reach the data file.
4. `GET` must never call `writeExpeditions()` — it is read-only.
5. Do not add a runtime `readReagentSites()` call inside either expedition handler. The seed
   file's coordinates are final at authoring time; re-coupling the two files at request time was
   explicitly rejected in `architecture-notes.md` and would reintroduce a dependency this feature
   deliberately avoids.

## Risks / Follow-ups

- If `reagent-sites.json`'s coordinates for the seeded sites ever change, `expeditions.json`'s
  seeded coordinates will go stale silently (no referential link, by design). Acceptable for a
  demo seed; flagged here, as `architecture-notes.md` already flagged, so it is not later mistaken
  for a bug.
- The read-modify-write pattern on `POST` is not safe under concurrent writes (two simultaneous
  `POST`s could race and one write could be lost). This is the same pre-existing characteristic of
  `writeOrders`/`writeUsers` today — not a new risk introduced by this feature, and out of
  scope.paths to fix.
- QA must snapshot-and-restore both `expeditions.json` and `users.json` around the test run (per
  `analysis.md`'s QA Task 4) — the data layer offers no isolation of its own; this is a test
  harness responsibility, not a schema one, but is noted here since it is this file's data that
  must stay unchanged after two consecutive test runs.
